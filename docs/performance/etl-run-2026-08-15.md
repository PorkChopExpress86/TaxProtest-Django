### Three numbers above that need reconciling

**`extra_features_detail1.txt` reports 905,338 loaded, but the table holds 871,769.** The ORM loader counts rows *offered* to `bulk_create`, not rows persisted, and it passes `ignore_conflicts=True` against `unique_feature_per_account (account_number, feature_code, feature_number)`. So 33,569 duplicate rows (3.7%) were silently dropped and still counted as loaded. The COPY paths do not have this gap — `real_acct` and `building_res` both report exactly what landed in the table. Worth knowing before trusting the ORM loader's `records_loaded` as a completeness signal.

**`extra_features_detail2.txt` is 100% invalid (361,592 rows, 0 loaded).** Verified, not a bug: sampled accounts from that file (`0010020000001`, `0010020000013`, `0010020000015`) have no `PropertyRecord` at all — HCAD splits extra features across the two detail files roughly by property type, and detail2 is the non-residential half. The loader correctly classifies every row as `invalid` (account absent from the residential map) rather than failing.

**`buildingdetail` gained 2,552 rows (+0.2%) against a byte-identical source.** The download stage confirmed all three archives unchanged upstream (size + `Last-Modified` match), and `propertyrecord` and `extrafeature` both reproduced their previous counts *exactly*. So the delta comes from the parser, not the data — the previous baseline was loaded by the old `transform.py`, this run by the new `row_reader`. The likeliest cause is the `QUOTE_NONE` policy: HCAD free-text fields carry raw unescaped quotes, and a reader using default quoting swallows subsequent lines until it finds a closing quote, silently losing rows. That would mean these 2,552 rows are *recovered*, not duplicated — but that is a hypothesis, and confirming it means diffing the two parsers over `building_res.txt`.

## Biggest remaining cost: `refresh_property_readiness`

At **3m 25.6s** this is now the single most expensive step in the pipeline — **34% of total wall clock**, more than the GIS load and the property load put together.

It is *not* the query shape. The `IN (SELECT …)` against `ParcelGeometry` plans as a healthy Hash Join. The function is two statements:

```sql
UPDATE data_propertyrecord SET is_data_ready = false WHERE is_data_ready = true;
UPDATE data_propertyrecord SET is_data_ready = true  FROM (…) WHERE …;
```

**In this run the first statement matched 0 rows.** `row_reader` writes `is_data_ready=False` for every property, so straight after the COPY the whole table is already false and only the second statement does work — 1,172,466 rows. Both statements only fire on a *standalone* re-run, where the table starts out correct; it is worth keeping the two cases apart when reasoning about this function's cost.

Why writing that many rows is so expensive: `is_data_ready` is indexed, so an update to it can never be a HOT update, and a non-HOT update inserts new entries into **all 13 indexes** on `data_propertyrecord` (~730MB worth).

The standalone path is the pathological one — measured on this table, clear-then-set costs **162s + 376s = 538s** to arrive at the state it was already in. `reconcile_property_data --apply` calls the function twice, so that is ~18 minutes of pure no-op.

### Fixed

Both passes are now guarded so they write only rows that actually change:

```sql
-- clear: only rows currently ready that no longer qualify
UPDATE … SET is_data_ready = false WHERE is_data_ready = true AND NOT (…);
-- set: the original statement, plus one restrictive predicate
UPDATE … SET is_data_ready = true  FROM (…) WHERE … AND is_data_ready = false;
```

| Path | Before | After |
|---|---:|---:|
| Standalone re-run (steady state) | 538s | **4.7s** |
| Full ETL (cold, every row false) | 206s | unchanged by construction |

The set pass is the *existing* statement with `AND is_data_ready = false` added. That predicate is purely restrictive, so on a cold run — straight after the property COPY, where `row_reader` has already written every row false — it matches exactly the same rows and plans the same way. The full-ETL path therefore cannot regress; the win is confined to the repeat callers, which is where the waste was.

Equivalence was checked against the old implementation's own output on the real table: running the new form over it changes **0 rows**, and the symmetric difference of the two ready-sets is **0 lost / 0 gained**.

## Environment finding: Postgres `/dev/shm` is 64MB

Surfaced while benchmarking, unrelated to the pipeline code. The `postgres` service in `docker-compose.yml` sets no `shm_size`, so it gets Docker's 64MB default. Postgres parallel workers allocate from there, and maintenance commands fail outright:

```
ERROR: could not resize shared memory segment "/PostgreSQL.3849131294"
       to 67145760 bytes: No space left on device
```

`VACUUM (ANALYZE) data_propertyrecord` fails this way; it only completes with `SET max_parallel_maintenance_workers = 0` (13.7s that way). Parallel *queries* hit the same ceiling — the comparables bounding-box scan runs with two parallel workers. Adding `shm_size: 1gb` to the postgres service is the standard fix. Not applied here: it is container configuration rather than pipeline code, and worth a deliberate decision.
